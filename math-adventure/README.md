## 1. 项目背景

### 1.1 背景

孩子目前7岁左右，就读小学二年级，课本数学基本没有问题。

家长希望进一步培养孩子的数学思维能力，尤其是：

- 逻辑推理能力
- 数学建模能力
- 数感与灵活计算能力
- 观察、归纳和寻找规律的能力
- 分类枚举与有序思考能力
- 逆向思维与问题转化能力
- 面对陌生问题时独立思考的能力

传统数学练习以做题、批改、纠错为主，趣味性不足。孩子比较喜欢获得奖励，因此希望将数学思维训练和游戏化成长机制结合起来。

### 1.2 产品目标

开发一套基于 **ESP32触摸屏 + 家长移动端H5 + 家庭服务器** 的数学思维冒险系统。

孩子通过ESP32触摸屏完成每天的数学思维挑战，获得经验值、金币、徽章等游戏奖励。

家长通过手机网页查看学习情况、分析思维能力发展，并管理题目和奖励。

产品不是电子作业本，而是一款以数学思维训练为核心的轻量级教育游戏。

### 1.3 核心理念

**让孩子因为喜欢冒险而主动开始学习，因为学会思考而获得成就感。**

设计原则：

1. 数学思维培养优先于刷题数量。
2. 鼓励思考过程，而不仅是正确答案。
3. 答错不惩罚、不扣经验、不掉级。
4. 奖励探索、坚持、解释和多种解法。
5. 每日训练适量，不诱导无限刷题。
6. 游戏应该有明确的完成状态。
7. 家长可以参与，但孩子能够独立完成基础挑战。
8. 数据属于家庭，优先私有化部署。

## 3. 硬件条件

### 3.1 已确认硬件

现有一块ESP32开发板：

- 屏幕尺寸：3.2英寸
- 支持触摸操作
- 计划横屏使用
- 已有Wi-Fi联网、配网及HTTPS上传代码

#### 现有固件核对（2026-11-20）

参考项目：[esp32-screen](../ink-screen/esp32-screen/README.md)。以下是仓库记录和代码配置，尚未进行本轮真机验证：

- README记录板型为LCDWIKI E32R32P；PlatformIO使用通用`esp32dev`构建目标，不能据此推断完整芯片、Flash或PSRAM规格。
- 现有框架为Arduino C++、PlatformIO，显示库为TFT_eSPI 2.5.43，JSON库为ArduinoJson 6.21.5，尚未接入LVGL。
- LCD配置为ST7789、240×320；当前`setRotation(0)`为竖屏。数学游戏计划采用320×240横屏布局，需真机验证方向及触摸坐标。
- LCD引脚已配置：MOSI=13、MISO=12、SCLK=14、CS=15、DC=2、背光=27，使用HSPI、20MHz。
- 启动代码将GPIO33标记为触摸片选并置高，但未实现触摸读取或校准；不能仅凭片选注释确认触摸芯片。
- 已有热点/网页配网、Preferences配置持久化、串口配置、断线重连、NTP校时、HTTPS根证书校验和失败重试，可作为复用基础。
- 当前业务为AHT20温湿度采集，使用GPIO32/25的I²C。已确认数学终端不保留温湿度功能；游戏固件移除采集、读数上传及对应状态界面，复用配网等基础能力。原采集项目保留作为参考，不在本次需求同步中删除。
- 当前上传使用共享`INK_TOKEN`，数学设备独立凭证仍需实现；采集队列仅保存在内存，不能直接作为答题重启恢复方案。
- 当前HTTP上传为同步调用，连接和读取超时各设置为5秒；游戏接入时需避免网络等待阻塞触摸和动画。

尚需确认：

- 实物是否与仓库记录的E32R32P板型及版本一致
- ESP32具体芯片与模组规格
- 触摸控制芯片、总线、引脚和横屏校准
- 是否有PSRAM
- Flash容量
- 喇叭型号、阻抗、额定功率、接口及板载功放规格
- 后续麦克风的型号、接口和供电需求
- 是否支持SD卡

显示配置以现有代码为起点，结合真机验证，不再从屏幕尺寸猜测分辨率。

### 3.2 ESP32职责

ESP32主要承担：

- 游戏画面展示
- 触摸交互
- 数学题展示
- 角色与怪物动画
- 闯关结果展示
- 经验、金币和奖励动画
- Wi-Fi连接
- 与服务器交换任务和答题数据

ESP32不负责：

- 大规模数学题库存储
- 最终积分计算
- 长期学习记录管理
- 数学能力统计分析
- 家长账户管理

### 3.3 固件技术建议

- C++
- PlatformIO
- 优先评估现有TFT_eSPI；是否引入LVGL需结合UI复杂度与可用内存确定
- 适配实际LCD和触摸驱动
- HTTP/HTTPS客户端
- JSON数据交换
- 轻量游戏精灵图与动画

复用现有显示、配网与网络代码；中文字体、图像资源、触摸驱动及是否引入LVGL，应在核实硬件与可用内存后确定。

### 3.4 音频输出与后续麦克风适配

已确认：先开发软件，声音适配放到下一步；终端之后连接喇叭，再扩展麦克风。当前仅保留扩展设计，不将音频硬件接入作为软件阶段验收前提。

**喇叭（下一步音频阶段）**

- 实现基础操作、答题反馈和通关音效，提供音量与静音设置并持久化；音效为辅助反馈，静音时仍可完成全部任务。
- 现有代码仅有GPIO4置高并注释为关闭音频功放的逻辑，尚无播放实现；功放型号、使能电平、音频输入方式和喇叭接法须依据板卡资料核对，不能仅凭注释决定接线。
- 在确认喇叭、功放和板卡规格后确定驱动、资源格式与存储方式；题目朗读可后续扩展，不视为首版已经具备的能力。

**麦克风（后续接入，首版预留）**

- 为音频输入和输出分离接口及配置，按实际硬件预留引脚、总线和内存预算；麦克风型号与接口尚未确定，不预先固定接线。
- 设计阶段核对屏幕、触摸、SD卡、音频输出与输入的资源占用。温湿度采集停用不代表原GPIO32/25可直接用于麦克风，仍须核对板级连接。
- 后续默认采用按住说话、松开结束的显式录音交互，显示录音状态并支持取消；是否用于口头讲解、语音答题或其他场景，接入前另行确认。
- 首版不要求语音识别或同时录放音；录音上传、保存规则与服务端识别接口在麦克风阶段确定。

**共同要求**

- 播放、后续采集与网络通信不能长时间阻塞触摸及画面更新。
- 无音频硬件或初始化失败时，显示可理解的状态并允许继续触摸答题。
- 真机联调验证音量、失真、供电稳定性及屏幕/触摸并行运行；音频驱动和引脚配置以确认的板型及外设资料为准。

## 4. 游戏世界设计

### 4.1 核心玩法

游戏采用轻量级RPG冒险模式。

基本循环：

```text
进入游戏
   ↓
看到自己的冒险角色
   ↓
进入世界地图
   ↓
选择数学关卡
   ↓
出现数学怪物
   ↓
阅读并理解题目
   ↓
选择答案 / 请求提示
   ↓
获得反馈
   ↓
完成挑战
   ↓
领取经验与金币
   ↓
解锁新的关卡
```

游戏应保留清晰的每日完成状态。

### 4.2 游戏地图

建议首版建立六个主题区域：

| 地图区域 | 数学主题       |
| ---- | ---------- |
| 凑整森林 | 数感、拆分、灵活计算 |
| 规律山谷 | 观察、归纳、数字规律 |
| 逻辑城堡 | 排除法、条件推理   |
| 图形秘境 | 图形观察、空间思维  |
| 智慧沙漠 | 分类枚举、组合    |
| 魔法之塔 | 逆向思维、综合挑战  |

地图的解锁与数学课程进度关联，而不完全依赖金币。

### 4.3 角色系统

首版角色为一名可爱的小魔法师，暂定名称“小语”。

角色属性：

- 当前等级
- 累计经验
- 当前金币
- 已解锁地图
- 徽章数量
- 已掌握的思维技能

角色可以随着学习逐渐升级。

未来可以扩展：

- 法杖
- 魔法帽
- 宠物
- 服饰
- 角色皮肤
- 城堡装饰

首版仅需一个基础角色形象。

### 4.4 怪物系统

每道数学题对应一个怪物挑战。

建议怪物风格：

- 可爱
- 轻松
- 有表情变化
- 不恐怖
- 不包含暴力画面

答题正确时，播放怪物被魔法净化、变成星星或宝箱的动画。

答错时，怪物仅做出可爱反馈，提示孩子重新思考。

### 4.5 游戏胜负规则

不使用传统的失败惩罚机制。

- 答对：关卡完成。
- 答错：可以继续尝试。
- 使用提示：仍可以通关。
- 多次尝试：仍可获取基础经验。
- 遇到困难：可以跳过并加入待复习列表。

不能让孩子因为一道难题长期卡关。

## 5. ESP32游戏界面

### 5.1 界面整体要求

屏幕采用横屏布局。

设计风格：

- 明确采用圆润、温暖的卡通绘本风格：奶油底色、草地绿、天空蓝、少量暖黄色；角色有圆脸、表情和简单动作
- 清晰、可爱的角色和怪物
- 明亮但不过度刺激的配色
- 文字尽可能简短
- 主要触摸按钮足够大
- 每个界面只聚焦一个主要操作
- 不照搬手机网页布局

根据实际分辨率适配字体、图片和触摸热区。

### 5.1.1 已确认的儿童友好规范（2026-11-22）

ESP32是孩子的冒险小伙伴。首版使用圆脸小魔法师和友善的森林精灵，挑战是“帮助朋友解开谜题”；不画攻击、血条、倒计时或失败惩罚。

- 按320×240横屏设计，安全边距8px，顶栏高28px，底部主要按钮高44px以上；按钮间至少留8px，按下有明显颜色变化，不依赖悬停。
- 中文正文至少16px，题干优先18～20px；题目过长按语义分页，不缩小到难以辨认。每页最多三个答案，支持更长内容的下一页；装饰不得遮挡题目。
- 中文使用实际字库，不使用系统emoji作为固件图标。角色、星星、金币、锁和网络标识使用轻量绘图或精灵图，状态同时配文字。
- 首页以角色、三颗任务星星和“开始冒险”为主；金币和等级退居顶栏。地图一次显示三个圆角关卡入口，锁定时解释“下一次冒险再来”。
- 答题页精灵缩到题干旁，保留大面积阅读空间；选项直接显示答案，底栏提供“想一想”和“稍后再来”，避免只有A/B/C的抽象操作。
- 答错说“再想一想，你可以的”，答对说“好办法！朋友谢谢你”；不使用红色大叉、刺耳反馈或负面评分。
- 结算先夸思考方法，再展示经验与金币；每日完成后显示“今天的冒险完成啦，休息一下吧”，主操作为“回家”，不无限引导下一题。
- 断网显示“正在找回小伙伴，请稍等”，保留当前题；提交中显示“正在送出答案”，不提前播放通关或发奖动画。重试复用同一请求ID，服务器确认后才更新奖励。
- 动画每次约300～800ms，不闪屏、不持续闪烁，不阻塞输入；静音和无音频硬件时体验完整。

首个画面实现位于[固件原型说明](firmware/README.md)。当前是明确标记的本地试玩版，已实现触摸校准、选关答题、提示、休息总结和本地进度保存；配网与服务端尚未接通，触摸及画面需真机验收。原温湿度固件保持独立，数学固件不包含采集逻辑。

## 6. 数学课程体系

### 6.1 总体规划

课程周期：24周。

建议每周4次，每次20～25分钟。

其中ESP32练习部分默认10～15分钟，剩余时间用于口头讲题、画图或亲子讨论。

每天默认3道题，可由家长调整。

### 6.2 六阶段课程

**第一阶段：数感与灵活思考（第1～4周）**

- 凑整
- 拆数
- 规律
- 数阵

**第二阶段：逻辑推理（第5～8周）**

- 排除法
- 顺序推理
- 条件推理
- 逻辑综合

**第三阶段：模型与画图（第9～12周）**

- 线段图
- 和差问题
- 逆向推理
- 等量代换

**第四阶段：分类与枚举（第13～16周）**

- 分类计数
- 搭配
- 数图形
- 不重复不遗漏

**第五阶段：经典奥数思维（第17～20周）**

- 间隔问题
- 周期规律
- 简单盈亏思想
- 等量与不变量

**第六阶段：综合挑战（第21～24周）**

- 一题多解
- 条件变化
- 综合推理
- 数学表达与总结

### 6.3 每道题的数据要求

每道题至少包含：

- 题目ID
- 题目内容
- 题型
- 选项（如适用）
- 正确答案与判定规则
- 数学主题
- 思维能力标签
- 适用年级
- 难度
- 分级提示
- 解析
- 所属课程
- 是否需要家长参与

题目应经过答案验证。

有多种合理答案的开放题，不应直接用简单字符串比较判错。

### 6.4 首批题库

已确认采用“先10道样题、再扩充至30道”的方式建设MVP题库，正式使用的题目均须人工审核通过。

覆盖：

- 灵活计算
- 数字规律
- 逻辑排除
- 顺序推理
- 简单逆推
- 画图理解数量关系

每道题需提供完整解析和至少一个提示。

不建议初期直接生成大量未经验证的AI题目。

### 6.5 题目来源与审核发布

当前本文档仅规划题库，不代表已有30道审核通过的题目。题库必须经过审核发布后才能用于孩子的正式任务。

已确认首批由Codex按二年级水平辅助起草，再逐题核算、审阅；也支持家长录入自编题或有使用授权的材料。不得自动抓取来源不明题库直接发布。记录每题来源类型、出处（如适用）及使用许可说明；AI起草的题目明确标记，AI起草不等于审核通过。

已确认流程：草稿 → 自动检查 → 待人工审核 → 已发布；自动检查失败留在草稿，人工审核不通过退回草稿，发现问题可停用。每日任务只能选择已发布且未停用的题目版本。

审核分两层：

1. 自动检查：必填字段完整、题型结构合法、选项与答案一致、数字计算及判定规则可验证；自动检查通过仅表示可提交人工审核。
2. 人工审核：审核者独立解题，核对条件是否充分、有无歧义、答案是否唯一或是否覆盖合理解法、解析与提示是否正确、语言和难度是否适合二年级，以及小屏幕能否清晰展示。

人工审核由家长或家长指定的具备相应解题能力的人执行；不能将AI复核或程序校验标为人工审核。数学结论、解析及提示可在开发时辅助校验，最终发布须经人工确认。

家长题目管理必须提供预览、审核通过、退回及停用操作，显示来源、自动检查结果和审核意见。记录题目版本、审核人、审核时间及发布时间；已发布内容修改后生成新版本并重新审核，历史答题记录关联原版本。

首批题库实施顺序：

1. Codex先起草10道样题，围绕凑整与灵活计算、数字规律、逻辑推理等主题，提供答案、完整解析、至少一个提示、能力标签、难度及来源标记。
2. 完成自动检查与辅助核算后，将样题提交给家长审核；由家长确认题目风格、难度与表述是否适合孩子，意见未确认前不擅自视为审核通过。
3. 按反馈修改样题，确认标准后再扩充至30道；新增题目同样逐题审核，通过一批发布一批。
4. 未完成审核时，开发联调使用明确标记的测试题和测试记录，不混入孩子的正式学习数据。

## 7. 游戏积分与奖励系统

### 7.1 双积分体系

使用两种独立的积分。

**经验值 XP**

用于角色升级和长期成长。

特点：

- 永不扣除
- 不可消费
- 不因答错减少
- 升级后保留累计经验

**金币 Coins**

用于兑换奖励。

特点：

- 完成指定任务获得
- 可以累计
- 可以兑换
- 由服务端记录流水
- 家长可配置兑换项目

### 7.2 首版奖励建议

| 事件       | 奖励     |
| -------- | ------ |
| 首次完成一道题  | +20 XP |
| 完成当天全部任务 | +10 XP |
| 首次独立答对   | +5金币   |
| 认真解释解法   | +5 XP  |
| 发现另一种解法  | +5金币   |
| 每周完成4次训练 | 解锁徽章   |

说明：

- 普通题目重复练习不重复获得通关奖励。
- 认真解释和一题多解由家长确认。
- 每日金币发放设置上限。
- 奖励规则由服务端集中管理。
- 金币兑换需要家长确认。
- 不设置断签惩罚。

### 7.3 等级系统

MVP可采用简单升级规则：

- 每累计100 XP升一级。
- 初始等级为1级。
- 等级根据累计经验计算。

未来可以调整为逐级增加升级所需经验。

### 7.4 奖励兑换

家长端配置奖励，例如：

| 奖励          | 所需金币 |
| ----------- | ---- |
| 选择一次家庭游戏    | 50   |
| 周末选择一次亲子活动  | 100  |
| 解锁一套游戏角色装扮  | 80   |
| 获得一个特别的冒险称号 | 60   |

不建议把所有学习行为与物质奖励绑定。

优先提供体验型、亲子互动型以及游戏内装饰奖励。

## 10. API设计草案

### 10.1 设备接口

```http
GET /api/math/device/state
GET /api/math/adventure/today
GET /api/math/questions/{id}
POST /api/math/answers
POST /api/math/device/heartbeat
```

答题示例：

```json
{
  "device_id": "esp32-math-001",
  "task_id": "task-1001",
  "question_id": "q-1001",
  "answer": "B",
  "request_id": "unique-request-id"
}
```

返回示例：

```json
{
  "correct": true,
  "task_completed": true,
  "reward": {
    "xp": 20,
    "coins": 5
  },
  "player": {
    "level": 3,
    "total_xp": 255,
    "coin_balance": 45
  },
  "explanation": "先计算27+13，再加38。"
}
```

注意：以上仅为接口示例，不代表已经实现。

`request_id`用于幂等控制，防止设备重试导致重复奖励。

### 10.2 家长接口

```http
GET  /api/math/parent/dashboard
GET  /api/math/parent/progress
GET  /api/math/parent/attempts
GET  /api/math/parent/review

GET  /api/math/rewards
POST /api/math/rewards
POST /api/math/rewards/redeem
POST /api/math/rewards/approve

GET  /api/math/tasks
POST /api/math/tasks/generate
```

### 10.3 安全设计

- 家长端必须认证。
- 家长操作需要校验对应孩子的访问权限。
- ESP32使用独立设备凭证。
- 设备凭证不能直接授权管理家长账户。
- 禁止客户端修改经验或金币余额。
- 发奖操作使用事务与幂等校验。
- 手机端与设备端分别控制接口权限。
- 不公开孩子的真实姓名和学习记录。
- 外网访问优先采用HTTPS。
- 设备配网及凭证写入需要独立设计。

## 12. 关键教育设计要求

这一部分非常重要，开发时不得忽略。

### 12.1 不把学习变成纯粹刷分

经验值和金币只是激励机制。

系统真正关注：

- 孩子是否理解题目
- 是否能独立推理
- 是否尝试不同方法
- 是否能解释自己的思路
- 是否能发现错误并修正

### 12.2 支持孩子解释过程

不能将全部数学思维题都设计成单纯选A/B/C。

后续增加：

- 口头解释
- 画图
- 数字输入
- 分类排序
- 多种答案
- 家长确认思维过程

### 12.3 控制学习时间

建议：

- 默认每天3题
- 默认10～15分钟设备练习
- 家长可调整
- 完成任务后显示明确的结束状态
- 不通过连续失败强迫重复做题
- 不因中断连续学习而扣除已有奖励

### 12.4 游戏反馈

成功时：

- 鼓励努力和方法
- 展示获得的奖励
- 用轻量动画庆祝

失败时：

- 不嘲讽
- 不扣分
- 允许重新尝试
- 提供必要提示
- 允许稍后继续

## 16. 给Codex的开发指令

请阅读本文档，并以现有pixel-app代码仓库为基础实施“小语数学冒险岛”。

### 开发原则

1. 不要重新创建一个与pixel-app无关的独立系统。
2. 先分析现有项目结构和技术栈。
3. 尽可能复用现有数据库、用户认证、后端服务、前端组件和Docker部署。
4. 保持代码模块化，不破坏现有功能。
5. 先实现可验证的MVP，再逐步增加游戏功能。
6. 新增API应有明确的数据结构和错误处理。
7. 积分结算必须由服务端完成，并具备幂等性。
8. 涉及硬件驱动的部分，先参考现有esp32-screen配置，核对实物板型及尚未实现的触摸驱动。
9. 禁止在未知硬件型号的情况下假定引脚和触摸驱动配置。
10. 对尚未实现的功能明确标注，不允许用静态Mock冒充真实联动。

### 首次开发任务

先完成以下工作：

**任务一：项目分析**

阅读现有pixel-app代码，明确前后端结构及可以复用的组件。

**任务二：MVP技术方案**

给出与现有系统匹配的模块设计、目录规划、接口清单与数据库迁移方案。

**任务三：移动端家长页面**

在现有前端项目中实现“小语数学冒险岛”家长端初版，包括：

- 今日战报
- 学习进度
- 经验与金币
- 答题记录
- 思维成长概况

保留现有项目风格，加入适当的游戏化视觉元素。

**任务四：开发基础服务端**

实现题库、审核发布、任务、答题记录、积分结算、家长查询接口。题库按第6.5节先提交10道样题供家长审核，确认后扩充至30道，不能将测试题或AI起草题直接标为已审核。

**任务五：准备ESP32通信接口**

提供清晰的设备状态、任务获取、答题提交接口契约，为后续固件接入做好准备。

### 暂时不要做的工作

- 不要实现复杂AI自动出题。
- 不要实现大型RPG游戏引擎。
- 不要引入不必要的微服务。
- 不要重建已有用户管理系统。
- 不要脱离现有固件猜测LCD或触摸驱动；新增触摸配置须有板型资料或实测依据。
- 不要一次性实现全部24周课程。

### 最终要求

完成第一阶段后，应能够在手机浏览器中打开家长端，看到由真实后端管理的模拟孩子学习数据，并通过API模拟ESP32答题行为，验证完整的任务、判题、奖励与进度同步流程。

在真实ESP32固件接入之前，可以使用API测试脚本或模拟设备客户端测试，但必须与正式业务接口保持一致。

## 17. 长期愿景

小语数学冒险岛不只是一个数学答题游戏。

它最终可以发展成一套家庭个性化学习终端：

- 通过ESP32进行短时、专注的学习交互。
- 通过pixel-app管理学习记录和成长过程。
- 使用AI辅助家长分析孩子常见的思维困难。
- 根据孩子的掌握情况逐步调整练习内容。
- 用游戏化方式维持兴趣。
- 将奖励重点放在努力、推理、创造力和真正的理解上。

最终目标：

**让孩子形成独立思考、喜欢探索、敢于面对难题的数学学习习惯，而不是单纯追求数学题做得快、做得多。**

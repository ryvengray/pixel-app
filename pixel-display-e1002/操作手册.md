# E1002 操作手册

目标：先让 E1002 显示一条中文消息，再接入 pixel-app。按顺序完成，每一步达到“检查结果”后再继续。

当前固件是待实机验证的原型，尚未完成编译、烧录及屏幕验证。本手册基于仓库现有实现；遇到编译错误时先保留完整日志。

## 1. 准备设备和环境

准备：

- reTerminal E1002、能传输数据的 USB 线和稳定供电。
- 一台 Ubuntu 主机，用于运行服务端，后续保持开机。
- 一台刷机电脑（可用当前 Mac），安装 VS Code 和 PlatformIO IDE 扩展。
- 设备可连接的 2.4 GHz Wi-Fi，设备与 Ubuntu 主机能在局域网内互相访问。

Ubuntu 需安装 Docker Engine 和 Docker Compose 插件。先执行：

```sh
docker --version
docker compose version
```

检查结果：两条命令都能输出版本。若提示权限不足，可用 `sudo docker ...` 执行后续 Docker 命令；若命令不存在，先完成对应工具安装。

本项目使用明文 HTTP 和匿名 MQTT，只用于可信局域网，不要给路由器配置公网端口转发。

## 2. 把项目放到 Ubuntu

将本仓库中的整个 `pixel-display-e1002` 文件夹复制到 Ubuntu 的家目录。可以使用图形化文件传输工具；若从 Mac 终端复制，可在仓库根目录运行：

```sh
scp -r pixel-display-e1002 用户名@Ubuntu的IP:~/
```

将 `用户名` 和 `Ubuntu的IP` 换成实际值。后续标记为“Ubuntu”的命令都在 Ubuntu 终端执行；刷机命令在连接 USB 的电脑上执行。

Ubuntu：

```sh
cd ~/pixel-display-e1002
ls
hostname -I
```

检查结果：能看到 `docker-compose.yml`、`server`、`firmware` 等。记下 Ubuntu 可被局域网访问的 IP，例如 `192.168.1.10`；不要选 Docker 虚拟网卡地址。建议在路由器里为 Ubuntu 固定 DHCP 地址。

## 3. 配置服务端令牌

Ubuntu：

```sh
cp .env.example .env
openssl rand -hex 32
nano .env
```

将生成的随机字符串填入文件：

```ini
PIXEL_TOKEN=这里填写刚生成的随机字符串
API_BIND=0.0.0.0
MQTT_BIND=0.0.0.0
```

在 nano 中按 Ctrl+O、回车保存，再按 Ctrl+X 退出。令牌需要在固件中使用，请妥善保存，不要提交到 Git 或分享。

检查结果：`.env` 已保存，`PIXEL_TOKEN` 不再是示例值。后续重新部署时不要重复复制示例文件覆盖它。

## 4. 启动服务端

Ubuntu，在 `~/pixel-display-e1002` 目录：

```sh
docker compose up --build -d
docker compose ps
curl http://127.0.0.1:18000/health
```

首次构建需要联网下载镜像、Python 依赖及字体，可能耗时数分钟。

检查结果：`api` 和 `mosquitto` 均运行；健康接口返回 `"ok":true`。`mqtt_connected` 应最终为 `true`，刚启动时为 `false` 可以稍等后再查。

再在刷机电脑浏览器打开以下地址，将 IP 替换为 Ubuntu 的实际地址：

```text
http://192.168.1.10:18000/health
```

检查结果：另一台电脑也能看到健康接口的 JSON。若失败，先检查 IP、访客 Wi-Fi 隔离和 Ubuntu 防火墙；需要允许可信局域网访问 TCP 18000 和 1883。不要直接关闭整个防火墙。

## 5. 配置设备固件

在刷机电脑上，用 VS Code 打开 `pixel-display-e1002/firmware` 文件夹，等待 PlatformIO 初始化。在文件列表中，将 `include/config.example.h` 复制为同目录的 `config.h`。

编辑 `include/config.h`，参考：

```cpp
#pragma once
#define WIFI_SSID "你的2.4GHz无线网络名称"
#define WIFI_PASSWORD "你的无线网络密码"
#define API_BASE "http://192.168.1.10:18000"
#define API_TOKEN "与Ubuntu的.env中完全相同的令牌"
#define MQTT_HOST "192.168.1.10"
#define MQTT_PORT 1883
#define DEVICE_ID "desk-01"
#define POLL_INTERVAL_MS 60000UL
```

替换 Wi-Fi、IP 和令牌。`API_BASE` 包含 `http://` 和 `:18000`；`MQTT_HOST` 只填 IP。`DEVICE_ID` 暂时保持 `desk-01`，与后续测试一致。不要用 `localhost` 代替 Ubuntu IP。

检查结果：两个 IP 都指向 Ubuntu，令牌与 `.env` 完全一致，字符串两侧保留英文双引号。密码若含双引号或反斜杠，需要按 C++ 字符串规则转义。

## 6. 编译固件

打开 VS Code 的 PlatformIO 终端，确认当前目录为 `firmware`，执行：

```sh
pio run -e e1002
```

也可以使用 PlatformIO 的 Build 按钮。首次编译需要联网下载工具链和 Seeed 驱动。

检查结果：出现 `SUCCESS`。如果失败，不要继续烧录，保存从第一条错误开始的完整日志。此版本依赖的 Seeed 驱动尚待编译验证，错误可能需要修改代码或固定依赖版本解决。

## 7. 连接 USB 并烧录

用数据线将 E1002 连接到刷机电脑，在 PlatformIO 终端执行：

```sh
pio device list
pio run -e e1002 -t upload
```

检查结果：检测到设备串口，烧录结果为 `SUCCESS`。如果有多个串口，可以显式指定实际端口：

```sh
pio run -e e1002 -t upload --upload-port 实际串口路径
```

若检测不到设备，先换数据线或 USB 接口，并按设备官方入门指南确认 USB 连接和下载模式，不要靠猜测操作按键。

烧录后打开串口监视：

```sh
pio device monitor -b 115200
```

必要时重启设备，保持 USB 稳定供电。监视器可用 Ctrl+C 退出。固件没有专门的 Wi-Fi 连接成功提示，无日志不能单独证明联网成功。

## 8. 发送第一条消息

回到 Ubuntu，在 `~/pixel-display-e1002` 目录执行。先输入与 `.env` 相同的令牌：

```sh
read -r -s -p '请输入 PIXEL_TOKEN: ' TOKEN
printf '\n'
curl -sS -X POST http://127.0.0.1:18000/v1/devices/desk-01/display \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"title":"你好，E1002","body":"第一条测试消息\n这是一块六色墨水屏。","title_color":"blue"}'
```

以上 `read` 命令适用于 Ubuntu 默认的 Bash 终端，输入令牌时不会显示字符。

检查结果：接口返回包含 `version` 的 JSON。此时只代表服务端保存成功，还需要等待设备刷新。不要反复提交；轮询及刷新限速可能使更新延后，先等待约两分钟并观察串口。

## 9. 确认屏幕更新成功

在同一个 Ubuntu 终端执行：

```sh
curl -sS http://127.0.0.1:18000/v1/devices/desk-01/desired \
  -H "Authorization: Bearer $TOKEN"
```

同时满足以下条件才算首次联调完成：

- `displayed_version` 与 `version` 一致，`status` 为 `displayed`。
- 设备串口出现 `displayed` 后跟版本字符串，确认请求通常输出 `ack HTTP 200`。
- 亲眼看到屏幕显示正确的中文、方向和颜色。

刷新过程中的闪烁先等它完成，不要中途断电。程序确认不能替代肉眼检查。

## 10. 修改显示内容

重复第 8 步的 POST 命令，修改 `title`、`body` 和 `title_color`。颜色可用 `black`、`white`、`red`、`yellow`、`green`、`blue`；正文固定黑色。正文中的 `\n` 表示换行。建议标题简短、正文先用几行，过长内容会截断。

设备上一次刷新完成后至少等待 60 秒才会启动下一次刷新，密集提交时只保证最终画面。

## 11. 可选：验证 Python 调用

在能访问 Ubuntu 的电脑上，进入 `pixel-display-e1002` 目录，设置环境变量。将地址和令牌替换为实际值：

```sh
export PIXEL_API_BASE='http://192.168.1.10:18000'
export PIXEL_TOKEN='实际令牌'
python3 examples/pixel_app.py
```

检查结果：接口返回版本，稍后屏幕显示示例消息。这个脚本验证 Python 调用链路；真正接入 pixel-app 时，还需按其框架注册 `examples/pixel_app.py` 中的 `TOOL_SCHEMA` 和 `display_text` 函数。

## 12. 日常管理和排错

以下命令在 Ubuntu 的 `~/pixel-display-e1002` 目录执行：

| 目的 | 命令 |
| --- | --- |
| 查看运行状态 | `docker compose ps` |
| 查看最近日志 | `docker compose logs --tail=100 api mosquitto` |
| 持续查看日志 | `docker compose logs -f api mosquitto`，Ctrl+C 退出 |
| 重启服务 | `docker compose restart` |
| 修改 `.env` 后应用配置 | `docker compose up -d` |
| 修改服务端代码后重新构建 | `docker compose up --build -d` |
| 停止服务并保留数据 | `docker compose down` |
| 再次启动 | `docker compose up -d` |

不要使用 `docker compose down -v`，除非你确实要删除保存的画面和设备状态。

| 现象 | 优先检查 |
| --- | --- |
| 健康接口访问失败 | 容器状态、Ubuntu IP、18000 端口和防火墙 |
| HTTP 401 | 请求令牌、固件 `API_TOKEN`、服务端 `.env` 是否一致；修改固件后需重新编译烧录 |
| `desired HTTP` 后为负数 | 设备 Wi-Fi、服务器地址和 HTTP 连通性 |
| `mqtt_connected` 持续为 false | `mosquitto` 容器日志和服务端日志 |
| 服务端已保存但设备未刷新 | 2.4 GHz Wi-Fi、设备 ID、1883 端口；等待一次轮询并观察串口 |
| `download or SHA-256 failed` | 网络稳定性、服务端日志；暂时停止连续提交 |
| `frame allocation failed` | 保留串口日志，检查 PSRAM 和开发板配置 |
| 状态为 displayed 但画面错误 | 拍下画面并保存串口日志，需要检查驱动、颜色映射或方向 |
| 烧录成功但设备无反应 | 供电、串口、启动日志及官方屏幕示例；目前固件仍待实机验证 |

需要协助时，提供失败步骤、完整错误日志、容器状态和屏幕现象，隐去令牌及 Wi-Fi 密码。
